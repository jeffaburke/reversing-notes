We once again will be using `/bin/cat` and our replacement of `cat` from the last module taking out the puts line.

Here we will cover the first three parts of a process.

What is a process?
- Every program on your computer runs as a process. Most browsers have one process per tab.
- Every Linux Process has these attributes:
	- state (running, waiting (waiting for a resource), stopped (backgrounded), zombie).
	- priority (high/low)
		- What is the importance of scheduling this process.
	- parents (process that created the process), siblings (processes the parent created that isnt the current one), children (processes that our process created)
	- shared resources (files, pipes, sockets)
	- virtual memory space
	- security context
		- EUID and EGID
		- Saved UID and GID
		- Capabilities
- Where do processes come from
	- We have an original process and then something happens and a new process is created.
	- A process will call an operating system functionality like a kernel call and it will copy the process more or less. Running `/bin/cat` the terminal will fork into a parent and child and the child will replace itself using the clone system call replacing itself with `/bin/cat`.

Process Lifecycle (In terms of `cat`)

1. Process is created as discussed above
2. Cat is loaded
	- Can we load, the kernel will check for executable permissions. If the file is not executable `execve` will fail
	- What to load?
		- The kernel will look at the file, does it start with a shebang if so it will be treated as a script file. The kernel will extract the interpreter from the shebang line and then use the interpreter to run the rest of the file. The interpreter can also be a shell script.
		- If not a script then it will for if the file matches the binary configuration in `/proc/sys/fs/binfmt_misc` and then the kernel will execute the interpreter specified for that format with the original file as an argument. If we do `ls /proc/sys/fs/binfmt_misc` we will see a whole bunch of different formats. These files look for different magic numbers. For example the `jar` format looks for the magic number `504b0304` and if we look at `\x50\x4b` we can see that this renders to PK.
		- If none of the `binfmt_misc` configurations are matched and there is a dynamically linked ELF the kernel reads the interpreter/loader defined in the ELF, loads the interpreter and the original file and lets the interpreter take control.
			- Process loading is done by the ELF interpreter specified in the binary.
			  `readelf -a /bin/cat | grep interpret` will give us the specified interpreter or "the loader". This can be overridden `/lib64/ld-linux-x86-64.so.2 /bin/cat flag` or permanently changed with `patchelf --set-interpreter`
				- If we use `patchelf` and set the interpreter to a nonexistent file the kernel will open our file see the interpreter then it tries to load the interpreter if fails then the kernel returns from `execve` execution saying there is no such file.
				- `ldd` will show what libraries an ELF depends on and we can see the  interpreter from there.
			- After the program and interpreter are loaded by the kernel now the interpreter locates the libraries. It will look in various places, by default we only look towards the end of this process where it looks in the system wide configuration (`/etc/ld.so.conf`) then it will look at `/lib` and `/usr/lib`. `LD_PRELOAD` can be used to define a path to an environment variable to a path to a library to help with debugging. `LD_LIBRARY_PATH` will add an additional path to search for libraries before using the system wide configuration. `DT_RUNPATH` or `DT_RPATH` specified in the binary file can point to specific library paths.
			- Then the interpreter loads the libraries
				- A relocation can take place where a library may need to be updated or contains a pointer to a resource if it is in a new place then the pointer address is updated.
				- `strace` will show the system calls made by a program.
				- 
				  ```c
				  int read( int fd, char buf*, int n)
				  {
					  buf[0] = 'p';
					  buf[1] = 'w';
					  buf[2] = 'n';
					  buf[3] = 'e';
					  buf[4] = 'd';
					  buf[5] = '\n';
					  return 6;
				  }
				  ```
				- We can then compile this with `gcc`
				  `gcc -shared -o preload.so preload.c`
				- Then update the `LD_PRELOAD` variable to pull this read function instead of the one linked.
				  `LD_PRELOAD=./preload.so ./cat ./cat.c` If we then run this we see `pwned` over and over again for every time the `read` function was called. We can do `strace -E` to pass `LD_PRELOAD` we can see the syscalls one thing to note is that we can see the environment variables with the exec call and the `var` number. We notice it increases by one when running `LD_PRELOAD`.
				- We can also use `patchelf --set-rpath /some/runpath ./cat` and now it will check for the libraries in this path as well.
				- Where does it get loaded into? Each process has a virtual memory space which contains the following:
					- The binary
					- The libraries
					- The "heap" (for dynamically allocated memory)
					- The "stack" (for function local variables)
					- any memory specifically mapped by the program
					- some helper regions
					- kernel code in the "upper half" of memory inaccessible by the process.
				- Virtual memory is dedicated to our process, physical memory is shared among the whole system.
				- `/proc/self/maps` can demonstrate this whole space.
		- If its a statically-linked ELF the kernel will load it
			- Loading process... the binary is loaded. We can compile a static version with `gcc`
			  `gcc -Wno-implicit-function-declaration -static -o cat-static cat.c`
			- The difference in size of the two binaries is HUGE. Rust supports static linking via Rust libraries although C libraries can still be pulled in dynamically.
			- `-static-pie` in `gcc` will allow for a statically linked executable to be positionally independent thus changing the virtual memory address on every run.
		- Other legacy file formats are checked for.
	- Interesting to note the loaders can be recursive.
3. Cat is initialized
	- Every ELF binary can specify constructors, which are functions that run before the program is actually launched. We can add our own constructors as well putting this at the top of our `cat.c` file it will now print `haha!` before reading the file.
	  ```c
	  __attribute__((constructor)) void haha()
	  {
		  write(1, "haha!\n", 6);
	  }
	  ```
	- This is useful with `LD_PRELOADing` so if we edit our `preload.c` file adding the same constructor then recompile it.
