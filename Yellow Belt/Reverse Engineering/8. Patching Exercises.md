#### Static Analysis

When looking at the program given the challenge description it can be assumed that the challenge will let you modify 5 bytes. Assuming it is similar to the crackmes we just did I will patch out the check if the license is correct replacing it with NOPs and hopefully the challenge will be solved.

![](Attachments/Pasted%20image%2020261002123040.png)

The program seems to do the patching for us which is cool, it seems to grab the base address for the program. 

![700](Attachments/Pasted%20image%2020261002123142.png)

The program seems to patch itself so this will be rather easy we just need to find the comparison functionality before the win check.

![](Attachments/Pasted%20image%2020261002123234.png)

Here the BinaryNinja base address is set to `0x400000` thus the offset we are targeting is `0x28d5`. I turned Opcodes on to see how many bytes we need to `nop` and if this is in the 5-byte limit. We see the opcode for the `jne` is two bytes. It shows the `75` meaning that it is a `jne` then the `14` is the offset to the `jmp` address. Since `RIP` would be `0x28d7` adding `0x14` would be `0x28eb` [(added this as I just learned this)](https://www.felixcloutier.com/x86/jcc).

Point being we could change `0x28d5` to `0x90` and do the same with `0x28d6` thus bringing us to the win condition.
#### Solving the Challenge

Doing exactly as described above we get the flag.

![](Attachments/Pasted%20image%2020261002124217.png)

Going a bit further I think changing the offset to `0x00` for the `jne` would also pass the challenge, thus only needing to change one byte.

![](Attachments/Pasted%20image%2020261002124359.png)

This also works as intended. Pretty nifty. Changing `0x00` is irrelevant as this part of the program has already been passed.

## Perfect Patch (Easy)

### Initial Exploitation

#### Static Analysis

The challenge for this challenge says we can patch two bytes but there is an integrity check of the flag afterwards.

![](Attachments/Pasted%20image%2020261002132713.png)

We just have to patch out the integrity check. Then we can patch out the key check.

![](Attachments/Pasted%20image%2020261002132801.png)

#### Solving the Challenge

Patching out both test's to be `cmp`'s allows the flag to be obtained.

![](Attachments/Pasted%20image%2020261002133028.png)

Skipping the check altogether I think `win` can be called with a patched `call`. We would need to find the offset between the two. Which is quite possible, then we have to take in endianness into account. 

Right after the patching check we see a call to `MD5_Init`

![700](Attachments/Pasted%20image%2020261002134159.png)

We should be able to find the offset from the RIP `1cc5` and the win function at `189d`. We need this offset to be negative as we are `call`ing to an address that is behind the current RIP. We can do `0x1cc5 - 0x189d` which equals `0x428`. Negating this result we get `0xFFFFFBD8`. This would be the new call address offset. So we should be able to patch `0x1cc1` to `0xD8` and `0x1cc2` to `0xFB`.

![](Attachments/Pasted%20image%2020261002134706.png)

Though the integrity check fails, we still get the flag. I like the different ways to wrap my head around this problem and constraints given the current problem.
