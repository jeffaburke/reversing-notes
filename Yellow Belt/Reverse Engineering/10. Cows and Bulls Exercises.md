# Cows and Bulls Exercises

## Background

Cows and Bulls is a classic code-breaking game where the objective is to correctly guess a random number. We will be required to reverse engineer a binary that plays a guessing game. Winning may not be as easy as it seems... The game tells you how many Cows you have aka right number but wrong spot, and how many bulls you have right number right spot when four digit combinations are entered.

#### Solving the Challenge

I started by running the binary and inputting each 4 number sequence in sequential order to see which combos led to potential Bulls and Cows.

![](Attachments/Pasted%20image%2020261014115913.png)

From the first guess to the second we know we must contain a `1` somewhere in the final combination as the 2 potential right numbers decreased to `1` after removing it, we can also say we will not have a 5.

When we introduce the `6` our potential right numbers goes back up to 2 meaning we must have a `6` somewhere in the mix. We can also say there is no 2 in the final combination.

Moving on from this the next guess `4567` doesn't change the amount of potential right numbers. We can't make any definitive assumptions off of this guess as we could have a 3 and 7 in the final combo so we move on.

Once the `4` gets bumped off and `8` gets brought in our potential right answers decreases meaning `4` must be in the final guess. Now that we have 3 potentially right numbers we can rule out the `3` and `7`. So we know our final combination must include `146` and not `23578`.

Bringing in the `9` count goes up again and that is our final number needed we just need to find where it may go.

Now we look at the bulls. `7890` has one bull meaning `xx9x` must be right. `4` must be in the last position as it was the only one with a bull `xx94`. `6789` had 1 bull and `1` cow, since we know where the `9` goes we can assume the bull was for the `6` and with that we get the combination `6194`.

Typing the combination in as our last guess we obtain the flag.

Breaking down the file format we can see that the hash of the Game ID is first in little endian (4 bytes). Next is the attempts in little endian as well as the length of the key (2 bytes and 2 bytes). From there the solution is given in the next 8 bytes. After that is the steps that need to be taken in order to get the flag. It gives an instruction for each step that is taken for example the first is `303043303342` or `00C03B`. Our earlier assumption about the `1234` being compared is wrong and this is seen when breaking on the `memcmp` instruction.

## Hashing Heifers

### Initial Exploitation

#### What is different?

In the new version of the program there is once again another added step for the user. In order to abuse this we will need to figure out what this new step is...

Looking through BinaryNinja we see the `memcmp` but just before it is a `SHA256` function call. This comes from `libcrypto` and this function takes three arguments. 

![](Attachments/Pasted%20image%2020261019181154.png)

![](Attachments/Pasted%20image%2020261019174239.png)

We also see that the format of the `gamefile.bin` has changed as well. When inspecting the file with `xxd` we once again see the header for the file and then we see what seems to be a similar format from the last challenge. Game ID, attempts, key length in little endian followed by the solution also in little endian and then we see a whole bunch of goop.

![](Attachments/Pasted%20image%2020261019174717.png)

Knowing we have a bunch of goop we can assume this is `SHA256` hashes that are checking against our input. Since I didn't trace the input of the hashing function we can open `gdb` to do this.

We set a break at the `SHA256` call to see what is hashed. We know that it is of key length 6 so we can assume it will be the `xxCxxB`.

```
break *($base("hashing-heifers") + 0x2018)
```

Breaking at this point we see that `RDI`'s first 6 bytes are indeed `303143303042` or `01C00B`. We can then use our game ID and search the hex dump of the `bin` file to see whether or not this is true. 

![](Attachments/Pasted%20image%2020261019175000.png)

This turns out to be true but now we should break at the `memcmp` to see what our hash is being compared to...

```
break *memcmp
```

## Salty Stampede

![](Attachments/Pasted%20image%2020261019184911.png)

Following this we see `6` padding bytes following by an array `0x0-0x21`. This is most likely the order of the keys to the correct guess.
