# Return Oriented Programming - Complications

## Issue 1: Limited Control

Sometimes our control of the stack is limited.
1. Limited overflow size
2. Inability to input `NULL` bytes. Often, we can still trigger one gadget

So can we win with one gadget?

## The Magic Gadget

We can....

Consider `system()`
- it has to set up a call to `execve("/bin/sh", {"/bin/sh", "-c", command}, env);`
- What if we jump partway through?

It works, if we get lucky with register values and stack setup, we can often trigger `/bin/sh` by jumping partway into `system()`. This location is called the magic gadget. This is often the go to thing because people want a shell, but we just need the flag so we could be looking for something like `chown` instead.

## Issue 4: Exotic Academic Solutions

ROP is part of a long-term cat and mouse game between attackers and defenders

Anti-ROP approaches:
- Removing ROP gadgets (too onerous): G-Free: Defeating ROP through Gadget-less Binaries
- Detecting ROP in progress (deployed but bypass-able): kBouncer Efficient and Transparent ROP mitigation. ROPecker: A generic and practical approach for defending against ROP attacks.
- Control Flow Integrity

## Control Flow Integrity

Core idea: Whenever a hijackable control flow occurs, make sure its target is something its supposed to be able to return to. This has spawned an arms race.

Counter-CFI Techniques:
- B(lock)OP: ROP on a block level by carefully compensating side-effects
- J(ump)OP: Instead of returns, use indirect jumps to control flow execute
- C(all)OP: Use indirect calls instead of returns
- S(ignreturn)ROP: Use the `sigreturn` syscall instead of returns
- D(ata)OP: Carefully overwrite the programs data

## Control Flow Integrity: Intel Edition

Intel in 2020 released processors with Control-flow Enforcement Technology (CET).

Among other things it adds the `endbr64` instruction. On CET-enabled CPUs, indirect jumps must end up at an endbr64 instruction or the program will terminate. This is still bypass-able by some advanced ROP techniques but it will significantly complicate execution.

## Issue: Hacking Blind

Can you exploit a program that you do not have? In certain situations, yes

Things are only randomized at program start time.

The standard blind attack requires a forking service.
- Break ASLR and the canary byte-by-byte. Now we can redirect memory semi-controllably.
- Redirect memory until we have a survival signal (address that doesn't crash).
- Use the survival signal to find non-crashing ROP gadgets.
- Find functionality to produce output.
- Leak the program.
- Hack it.
